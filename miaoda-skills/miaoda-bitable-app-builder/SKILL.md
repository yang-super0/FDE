# 妙搭+多维表格应用开发工作流

> **开工第一步**：先花 2 分钟过一遍 `QUICKSTART.md`（开工前速查卡，一页纯勾选），全部打勾再发第一条开发指令；本文件是完整流程，`references/` 是细节参考。

## 核心原则
- **先建飞书应用，再写代码** — 不配置原生API凭证，发布后写操作必失败
- **预览≠发布** — 编辑器预览正常不算完成，必须到线上正式地址验证
- **小步快跑·单模块闭环** — 一次只让 AI 做一个模块，开发→预览自测通过→再做下一个，禁止一次性生成全部模块（详见阶段5）

## 四条避坑铁律（来自真实项目复盘，优先级最高）
1. **凡字段必核验** — 字段名/类型/单选枚举以线上多维表格真实定义为准，开工前先拉取；禁止凭需求文档或字段名想当然（单选常被误当文本导致读取为空）。
2. **建表≠连通** — 每一张表都必须能指出"被哪个页面/哪个 AI 能力用到"，并实测取到数；表建好了但前台没接线等于没做。详见 `references/data-lineage.md`。
3. **确定性归规则，不确定才归 AI** — 筛选、排序、候选合并、兜底用确定性代码；AI 只负责生成文案/理由，且必须有空值兜底、结果校验，绝不把正确性押在 AI 一次生成上。详见 `references/ai-component-patterns.md`。
4. **编译通过≠功能正确，AI 自查≠真的通过** — LSP 无错、AI 说"自查通过"都不算数，必须以用户视角按验收点在正式地址逐项实测，并主动抓接口入参/出参核对。

## 8阶段严格工作流

按顺序执行，每阶段完成检查清单后才能进入下一阶段。

### 阶段1：需求分析
**目标**：将模糊需求转化为功能清单和数据模型。
**关键动作**：梳理角色场景 → 输出三张清单（页面/数据表/AI功能）→ 每条需求与清单一一对应 → 识别高风险字段（人员/关联/附件）
**交付物**：
- **页面清单**：每个页面的类型、数据来源、关键交互
- **数据表清单**：每张表承载什么实体、被哪些页面/AI 用到
- **AI 功能清单**：每个 AI 能力的输入、候选数据来源、输出结构
- 权限矩阵、高风险字段清单
**门禁**：三张清单与原始需求逐条对应、并经用户确认后才开工，避免早期跑偏。
**详细指南**：读取 `references/phase-1-requirements.md`

### 阶段2：多维表格设计
**目标**：设计稳定表结构，避免后期改字段。
**关键动作**：一表一实体 → 选择字段类型 → 录入测试数据 → 记录Base Token和table_id
**强制规则**：
- 小白第一版人员字段用文本、关联字段用文本、不做附件
- **建表后回读一次真实字段定义（字段名+类型+单选枚举），与设计假设核对**，后续代码以真实定义为准
**详细指南**：读取 `references/phase-2-bitable-design.md`、`references/field-adaptation.md`

### 阶段3：飞书自建应用配置 ⚠️ 最关键
**目标**：获取原生API凭证，保证发布环境写操作正常。
**关键动作**：创建自建应用 → 配置bitable:app权限 → 发布审批 → 测试tenant_access_token
**不做此步的后果**：发布后所有写操作报500 `kctx is nil`
**详细指南**：读取 `references/phase-3-feishu-app.md`

### 阶段4：妙搭应用创建与配置
**目标**：创建应用并配置数据源连接。
**关键动作**：新建应用 → 配置.env凭证 → 实现双通道数据层 → 配置字段映射
**强制规则**：
- `.env` 必须配置 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_BASE_TOKEN`
- `FeishuBitableClient` 必须在 `BitableService` 之前注册（否则误判原生通道不可用）
- 多张表时同步建立数据血缘表（表→插件→消费方），详见 `references/data-lineage.md`
**详细指南**：读取 `references/phase-4-miaoda-setup.md`

### 阶段5：开发实现（分模块小闭环）
**目标**：用AI按模块逐个生成应用，每个模块即开即测，完成字段适配和数据回填。
**关键动作**：
1. 先做模块切片与开发排序（数据层/字段适配 → 主表列表详情 → 其余表 → 搜索 → AI 能力 → 聚合收尾）
2. **一次只让 AI 开发一个模块**，提示词写清"本次范围/数据源/不做什么/完成先自测别发布"
3. 每个模块在预览环境自测通过（正常+边界+数据来源）后，再开发下一个，并要求不破坏已测模块
4. 实现关联字段标题回填、人员字段处理、统一接口格式
**必做项**：关联字段标题回填（原生API不返回标题，必须二次查询）
**AI 能力**：严格按四层模式（空值兜底→规则打底→提示词约束→结果校验兜底），读取 `references/ai-component-patterns.md`
**字段适配规则**：读取 `references/field-adaptation.md`
**详细指南（含分模块提示词模板）**：读取 `references/phase-5-development.md`

### 阶段6：测试验证
**目标**：模块自测之上做全量 + 跨模块联调，确保预览和发布环境都正常。
**关键动作**：
- 边界值必测：分类"全部"、空输入、无匹配结果、AI 返回空——这些分支最易漏
- 跨模块一致性：页面跳转、同一数据在不同页面口径一致、搜索/AI 候选覆盖所有相关表
- 抓接口核对：入参候选是否完整、出参是否非空（不只看页面）
- 发布环境重点测写操作
**发布环境必测**：新增返回201（非500）、关联字段标题非空、人员字段正常
**详细指南**：读取 `references/phase-6-testing.md`

### 阶段7：发布上线
**目标**：安全发布并保证迭代质量。
**关键动作**：发布前检查 → 执行发布（异步轮询，等到明确"发布成功"）→ 到**线上正式地址**做冒烟测试（打开+新增+删除+关键AI能力）
**每次发布后必做**：冒烟测试3项（打开页面、新增测试、删除测试），AI 类能力额外验证一次正常+一次边界
**详细指南**：读取 `references/phase-7-publish.md`

### 阶段8：运维迭代
**目标**：持续迭代不翻车。
**关键动作**：保留日志 → 小步迭代（继续按单模块闭环）→ 每次发布做冒烟测试 → 定期备份数据 → 改表结构后同步回读字段并更新适配层

## 问题排查

遇到问题时按此顺序：
1. 看妙搭「接口日志」红色报错，并抓问题接口的**入参/出参**（AI 类先看候选是否漏表、出参是否为空）
2. 检查 `.env` 凭证是否正确
3. 检查飞书应用权限是否审批
4. 回读多维表格真实字段名/类型，确认是否与代码匹配（警惕单选误当文本）
5. 对照数据血缘表，确认该表/该链路是否真的连通
6. 查阅常见坑解决方案

**常见坑完整列表**：读取 `references/pitfalls.md`
**多表连通**：读取 `references/data-lineage.md`
**AI 组件兜底**：读取 `references/ai-component-patterns.md`

## 关键技术决策

| 决策点 | 推荐方案 | 原因 |
|---|---|---|
| 数据通道 | 原生HTTP优先，插件兜底 | 插件通道发布环境写操作报kctx is nil |
| 人员字段 | 第一版用文本，熟练后再用人员类型 | 人员字段需要通讯录权限，复杂度高 |
| 关联字段 | 必须实现标题回填 | 原生API只返回record_id，不返回标题 |
| 附件字段 | 第一版省略；下载/预览必须接真实文件URL与正文 | 上传流程复杂，需要drive权限；禁止做不能用的UI壳子 |
| 字段类型 | 开工前回读真实定义再写映射 | 单选易被误当文本，凭假设会取空值 |
| 多表连通 | 建立血缘表，搜索/AI候选合并所有相关表 | 建表≠连通，漏表会导致搜不到/AI返回空 |
| AI 结果 | 规则打底+AI表达+空值兜底+结果校验 | 纯AI不稳定、会空返回、会编造，不能押注一次生成 |
| 开发节奏 | 单模块开发→自测→再开发，禁止一次性全量生成 | 一次性做完问题堆积、难定位、易互相破坏 |
| 发布验证 | 线上地址实测+抓接口，不信编译通过/AI自查 | 预览≠发布，编译过≠功能对 |
