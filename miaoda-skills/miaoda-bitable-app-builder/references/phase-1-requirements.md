# 阶段1：需求分析

## 目标
将模糊需求转化为可执行的功能清单和数据模型，并在开工前与用户对齐，避免早期跑偏。

## 执行步骤

### 1.1 角色与场景梳理
向用户确认3个问题：
- 谁用这个应用？（销售员/财务/管理员/客户）
- 每个角色每天要做什么操作？
- 核心业务流程是什么？（如下单→发货→收款→售后）

### 1.2 输出三张清单（并与原始需求逐条对应）
不要只写一个笼统功能列表，按下面三张清单拆分，**每条都要能回溯到需求原文**：

**① 页面清单**：按模块列出页面，每页标注类型、数据来源、关键交互
- 列表页（筛选条件、展示字段）
- 表单页（新增/编辑字段、验证规则）
- 详情页（展示信息、下载/跳转等真实操作）
- AI 页面 / 仪表盘（如有）

**② 数据表清单**：每张表标注承载的实体、以及"被哪些页面/AI 能力用到"
- 这一步直接防止"建了表但没接线"，多表连通方法见 `data-lineage.md`

**③ AI 功能清单**（如有）：逐个 AI 能力标注
- 输入字段、候选数据来自哪些表、输出结构
- AI 工程化要求见 `ai-component-patterns.md`

输出格式示例：
```
【订单管理】
- 页面：订单列表（按状态/日期筛选）、订单详情、新增订单表单
- 数据表：订单表→列表/详情/新增；客户表→关联下拉、客户详情
- AI：智能推荐（输入=客户行业；候选=商品表+案例表；输出=3条推荐+理由）
- 状态：待付款→待发货→已发货→已完成
```

### 1.3 风险字段识别
标记以下高风险字段类型，提前告知用户：
- **人员字段**：需要飞书通讯录权限，发布环境易出问题
- **关联字段**：原生API不返回标题，需额外回填逻辑
- **附件字段**：上传流程复杂，第一版建议省略；若只做下载/预览需接真实文件 URL
- **公式字段**：只读，不可写入
- **单选/多选字段**：记录全部枚举选项，提醒自己后续以线上真实类型为准（易被误当文本）

### 1.4 交付物
- 三张清单（页面 / 数据表 / AI 功能），且与需求逐条对应
- 角色权限矩阵（谁能看/改/删什么）
- 高风险字段清单

## 完成标准（门禁）
- [ ] 三张清单已输出，且每条都能对应到原始需求、无遗漏
- [ ] 每张数据表都已标注消费方（页面/AI），无"孤立表"
- [ ] 高风险字段已识别并告知用户
- [ ] 核心业务流程无歧义
- [ ] **清单已经用户确认，才进入阶段2（未确认不开工）**
