# 妙搭 + 内置 PostgreSQL 应用开发工作流

> **开工第一步**：先花 2 分钟过一遍 `QUICKSTART.md`（开工前速查卡，一页纯勾选），全部打勾再发第一条开发指令；本文件是完整流程，`references/` 是细节参考。

## 这个 Skill 和「妙搭+多维表格」的区别

| 维度 | 妙搭+多维表格 | 妙搭+内置 PostgreSQL（本 Skill） |
|------|-------------|--------------------------------|
| 数据存储 | 飞书多维表格（外部 SaaS） | 妙搭内置 Serverless PostgreSQL |
| 单次查询延迟 | 200~500ms（HTTP API） | 1~10ms（内网数据库） |
| 复杂查询 | 不支持 JOIN，需内存拼接 | 原生 SQL JOIN / 子查询 / 窗口函数 |
| 聚合统计 | 拉全量到内存算 | 原生 GROUP BY / SUM / COUNT |
| 事务 | 不支持 | 完整 ACID 事务支持 |
| 大数据量 | 单页 500 条，需多次分页 | 千万级行秒级响应（有索引） |
| 协作能力 | 多人在线编辑、评论、视图 | 无（需自己开发权限和界面） |
| 适用场景 | 协作型、轻量、快速搭建 | 高性能、复杂查询、数据量大 |

**选择原则**：需要多人协作编辑数据、用多维表格自带视图 → 选多维表格；追求性能、复杂查询、大数据量 → 选本方案。

## 核心原则

- **先设计表结构，再写代码** — 数据库表结构是应用的地基，设计不好后期改表成本高
- **索引先行** — 凡是 WHERE / JOIN / ORDER BY 用到的字段，必须建索引，否则数据量上来后查询会慢
- **小步快跑·单模块闭环** — 一次只让 AI 做一个模块，开发→预览自测通过→再做下一个，禁止一次性生成全部模块
- **预览≠发布** — 编辑器预览正常不算完成，必须到线上正式地址验证
- **善用分支和 Time Travel** — 妙搭 PostgreSQL 支持数据库分支和秒级回退，改表结构前先建分支，出问题一键回滚

## 四条避坑铁律（优先级最高）

1. **凡查询必看执行计划** — 慢查询先 `EXPLAIN ANALYZE`，不要凭感觉加索引或改 SQL；全表扫描是性能杀手
2. **N+1 查询是万恶之源** — 列表页查主表后逐条查关联表，必须改成 JOIN 或批量 IN 查询；详细排查见 `references/sql-best-practices.md`
3. **事务边界要清晰** — 多表写入必须包在事务里，避免部分成功部分失败；长事务会锁表，影响并发
4. **编译通过≠功能正确，AI 自查≠真的通过** — LSP 无错、AI 说"自查通过"都不算数，必须以用户视角按验收点在正式地址逐项实测，并主动查数据库确认数据正确

## 8 阶段严格工作流

按顺序执行，每阶段完成检查清单后才能进入下一阶段。

### 阶段1：需求分析
**目标**：将模糊需求转化为功能清单和数据模型。
**关键动作**：梳理角色场景 → 输出三张清单（页面/数据表/AI功能）→ 识别实体关系（1:1 / 1:N / N:N）→ 识别高风险操作（批量写入、长事务、并发更新）
**交付物**：
- **页面清单**：每个页面的类型、数据来源、关键交互
- **数据表清单**：每张表承载什么实体、字段、被哪些页面用到
- **实体关系图（ER 图）**：表之间的关联关系和外键
- **AI 功能清单**：每个 AI 能力的输入、输出结构
**门禁**：三张清单 + ER 图与原始需求逐条对应、并经用户确认后才开工。
**详细指南**：读取 `references/phase-1-requirements.md`

### 阶段2：数据库设计
**目标**：设计规范、高性能的表结构，避免后期改表。
**关键动作**：
1. 一表一实体，字段原子化（第一范式）
2. 选择合适的数据类型（VARCHAR 长度、NUMERIC 精度、TIMESTAMPTZ）
3. 主键用 `BIGSERIAL` 或 `UUID`，外键建立关联
4. **为所有 WHERE / JOIN / ORDER BY 字段建索引**（B-tree 为主，特殊场景用 GIN / GiST）
5. 加约束（NOT NULL / UNIQUE / CHECK / 外键约束）保证数据完整性
6. 写入测试数据（每表 20~50 条，含边界值）
7. 用 `EXPLAIN ANALYZE` 验证关键查询走索引
**强制规则**：
- 金额用 `NUMERIC(12,2)`，禁止用 FLOAT/REAL
- 时间用 `TIMESTAMPTZ`（带时区），禁止用 TIMESTAMP
- 软删除用 `deleted_at TIMESTAMPTZ NULL`，不要物理删除
- 所有表必须有 `created_at` 和 `updated_at`
**详细指南**：读取 `references/phase-2-database-design.md`、`references/sql-best-practices.md`

### 阶段3：妙搭应用创建与配置
**目标**：创建完整应用，确认内置 PostgreSQL 可用。
**关键动作**：
1. 访问 https://miaoda.feishu.cn，新建应用 → 选择「完整应用」（不是仅前端页面）
2. 确认应用已自动挂载 Serverless PostgreSQL 数据库
3. 配置环境变量（如 AI API Key、第三方服务凭证等）
4. 建立数据库分支策略：开发分支用于迭代，主分支用于生产
5. 记录数据库连接信息（通过妙搭 Open API 或后台查看）
**注意**：妙搭内置 PostgreSQL 是火山云 Serverless 版，支持：
- 秒级创建实例和分支
- Schema Diff 对比和安全合并
- Time Travel 秒级回退
- 非活跃自动释放资源
- AI 函数（`ai_query` 等，可在 SQL 中直接调用 AI）
**详细指南**：读取 `references/phase-3-miaoda-setup.md`

### 阶段4：开发实现（分模块小闭环）
**目标**：用 AI 按模块逐个生成应用，每个模块即开即测。
**关键动作**：
1. 先做模块切片与开发排序（数据层/ORM → 主表列表详情 → 其余表 → 搜索 → 统计 → AI 能力 → 聚合收尾）
2. **一次只让 AI 开发一个模块**，提示词写清"本次范围/数据表/不做什么/完成先自测别发布"
3. 每个模块在预览环境自测通过（正常+边界+数据来源）后，再开发下一个
4. 实现关联查询（用 JOIN 不要 N+1）、分页（LIMIT/OFFSET 或游标分页）、搜索（ILIKE / 全文检索）
5. 统计页面用原生 SQL 聚合（GROUP BY / 窗口函数），不要拉全量到内存算
**必做项**：
- 所有列表接口支持分页（page + page_size）
- 所有写操作使用事务（多表写入时）
- 所有用户输入参数化查询，禁止 SQL 拼接（防注入）
- 慢查询加索引，用 `EXPLAIN ANALYZE` 验证
**AI 能力**：严格按四层模式（空值兜底→规则打底→提示词约束→结果校验兜底），可利用 PostgreSQL 的 `ai_query` 函数在数据库层直接做 AI 处理
**详细指南（含分模块提示词模板）**：读取 `references/phase-4-development.md`

### 阶段5：测试验证
**目标**：模块自测之上做全量 + 跨模块联调，确保预览和发布环境都正常。
**关键动作**：
- 边界值必测：空输入、无匹配结果、分页边界、并发更新冲突——这些分支最易漏
- 跨模块一致性：页面跳转、同一数据在不同页面口径一致、搜索覆盖所有相关表
- 数据库级核对：操作后直接查数据库，确认数据正确（不只看页面）
- 性能测试：关键列表接口响应 < 500ms，统计接口 < 1s；超过则优化索引或 SQL
- 并发测试：多用户同时编辑同一条记录，确认不会脏写或丢失更新
**发布环境必测**：新增返回 201、编辑正常、删除正常（软删除）、关联查询正确、统计数据准确
**详细指南**：读取 `references/phase-5-testing.md`

### 阶段6：发布上线
**目标**：安全发布并保证迭代质量。
**关键动作**：
1. 发布前检查全部通过
2. 数据库 Schema 变更先在开发分支验证，再合并到主分支
3. 执行发布（异步轮询，等到明确"发布成功"）
4. 到**线上正式地址**做冒烟测试（打开+新增+编辑+删除+关键查询）
5. 确认数据库连接正常，无连接池耗尽
**每次发布后必做**：冒烟测试，确认数据库读写正常
**详细指南**：读取 `references/phase-6-publish.md`

### 阶段7：运维迭代
**目标**：持续迭代不翻车。
**关键动作**：
- 保留慢查询日志，定期优化
- 小步迭代（继续按单模块闭环）
- 每次发布做冒烟测试
- 定期备份数据（或利用 Time Travel 能力）
- 改表结构前先建数据库分支，验证后再合并
- 监控数据库连接数、存储用量、查询延迟

## 问题排查

遇到问题时按此顺序：
1. 看妙搭「接口日志」红色报错，确认是数据库错误还是应用错误
2. 数据库错误：看 SQL 语句和错误信息，直接在数据库中执行该 SQL 复现
3. 慢查询：用 `EXPLAIN ANALYZE` 看执行计划，确认是否走索引
4. 检查是否有 N+1 查询（列表页逐条查关联）
5. 检查事务是否过长、锁等待
6. 检查连接池是否耗尽
7. 查阅常见坑解决方案：`references/pitfalls.md`

## 关键技术决策

| 决策点 | 推荐方案 | 原因 |
|---|---|---|
| 数据源 | 妙搭内置 Serverless PostgreSQL | 性能好（1~10ms）、支持复杂查询、事务、索引 |
| 主键 | BIGSERIAL（自增）或 UUID | BIGSERIAL 性能好；UUID 适合分布式场景 |
| 金额字段 | NUMERIC(12,2) | 精确，不会有浮点误差 |
| 时间字段 | TIMESTAMPTZ | 带时区，避免时区混乱 |
| 删除方式 | 软删除（deleted_at） | 可恢复，有审计痕迹 |
| 关联查询 | 原生 SQL JOIN | 性能好，一次查询搞定，避免 N+1 |
| 分页 | LIMIT/OFFSET（小数据量）或游标分页（大数据量） | OFFSET 越深越慢，大数据量用游标 |
| 搜索 | ILIKE（短文本）或全文检索（长文本） | ILIKE 简单但不走索引；全文检索性能好 |
| 统计 | 原生 SQL GROUP BY / 窗口函数 | 数据库层计算，比拉到内存快 |
| 多表写入 | 事务（BEGIN / COMMIT） | 保证原子性，避免部分成功 |
| 用户输入 | 参数化查询（Prepared Statement） | 防 SQL 注入 |
| 索引 | B-tree（等值/范围）、GIN（数组/JSON/全文） | 按查询场景选合适索引类型 |
| 改表结构 | 先建数据库分支，验证后合并 | 利用妙搭分支能力，出问题可回退 |
| 开发节奏 | 单模块开发→自测→再开发，禁止一次性全量生成 | 一次性做完问题堆积、难定位 |
| 发布验证 | 线上地址实测+查数据库，不信编译通过/AI自查 | 预览≠发布，编译过≠数据对 |
