# 常见坑与解决方案

## 坑1：N+1 查询（最常见、影响最大）

- **现象**：列表页数据越多越慢，20 条数据要 2~3 秒
- **根因**：先查主表 20 条，然后循环 20 次逐条查关联表（客户名、商品名等）
- **解决方案**：
  - 一对一关联：用 JOIN 一次查出
  - 一对多关联：主表一次 + 从表用 `IN (id1, id2, ...)` 批量查一次
- **预防**：阶段4明确禁止 N+1，代码审查时看列表查询的 SQL
- **详细排查**：见 `sql-best-practices.md` 1.2 节

## 坑2：全表扫描（索引没建或没生效）

- **现象**：数据量小的时候快，数据上万后列表查询突然变慢
- **根因**：WHERE / JOIN / ORDER BY 的字段没建索引，或索引没生效
- **解决方案**：
  1. 用 `EXPLAIN ANALYZE` 看执行计划
  2. 如果是 `Seq Scan`，检查相关字段是否有索引
  3. 加索引后重新验证
- **索引没生效的常见原因**：
  - 字段类型不匹配（VARCHAR 字段传了 INTEGER）
  - 对索引字段用了函数（`WHERE LOWER(name) = 'xxx'`）
  - `LIKE '%xxx'` 前缀通配符
  - 数据量太小，优化器认为全表扫描更快（正常）
- **预防**：阶段2建表时为所有查询字段建索引，阶段5用 EXPLAIN 验证

## 坑3：拉全表不分页

- **现象**：列表页加载慢，甚至超时；内存占用高
- **根因**：`SELECT * FROM orders` 一次性拉所有数据，在代码里分页
- **解决方案**：用 `LIMIT + OFFSET` 数据库分页；深分页用游标分页
- **预防**：阶段4明确所有列表接口必须分页

## 坑4：统计查询拉全量到内存算

- **现象**：仪表盘加载慢，数据越大越慢
- **根因**：`SELECT * FROM orders` 然后在代码里循环 count / sum / group by
- **解决方案**：用原生 SQL `GROUP BY` / `SUM` / `COUNT` / 窗口函数，在数据库层计算
- **预防**：阶段4明确统计必须用 SQL 聚合

## 坑5：SQL 注入漏洞

- **现象**：安全扫描发现漏洞，或被攻击数据泄露/篡改
- **根因**：字符串拼接 SQL，如 `"SELECT * FROM users WHERE name = '" + input + "'"`
- **解决方案**：所有用户输入用参数化查询（Prepared Statement）
- **预防**：阶段4明确禁止 SQL 拼接，代码审查时查

## 坑6：金额用 FLOAT 导致精度误差

- **现象**：金额计算出现 0.1 + 0.2 = 0.30000000000000004，合计对不上
- **根因**：FLOAT / REAL 是二进制浮点数，十进制小数无法精确表示
- **解决方案**：金额用 `NUMERIC(12,2)`（或更高精度如 `NUMERIC(18,4)`）
- **预防**：阶段2建表时明确金额字段类型

## 坑7：时间用 TIMESTAMP 导致时区混乱

- **现象**：显示的时间差 8 小时，或不同用户看到的时间不一样
- **根因**：`TIMESTAMP` 不带时区，存入时按数据库时区，读出时按应用时区，容易混乱
- **解决方案**：用 `TIMESTAMPTZ`（带时区），统一存 UTC，前端按用户时区显示
- **预防**：阶段2建表时明确时间字段类型

## 坑8：多表写入不用事务，部分成功部分失败

- **现象**：订单建了但明细没建，或库存扣了但订单没建，数据不一致
- **根因**：多表写入没有包在事务里，中间某步失败后前面的已经提交
- **解决方案**：相关写入用 `BEGIN / COMMIT` 包起来，失败时 `ROLLBACK`
- **预防**：阶段4明确多表写入必须用事务，阶段5测试事务回滚

## 坑9：长事务锁表

- **现象**：某张表突然所有写入都卡住，等很久才超时
- **根因**：一个事务开了很久没提交（比如在事务里调外部 API、或循环大量插入），锁住了表或行
- **解决方案**：
  - 缩短事务，只把必要的数据库操作包在事务里
  - 不要在事务里调外部 API / 发消息 / 做耗时操作
  - 检查 `pg_locks` 看有没有未释放的锁
- **预防**：阶段4明确事务边界要清晰

## 坑10：软删除没过滤，已删除数据还显示

- **现象**：删除了的数据还在列表里出现，或统计数字包含已删除数据
- **根因**：用软删除（`deleted_at`）但查询时忘了加 `WHERE deleted_at IS NULL`
- **解决方案**：所有查询都加 `WHERE deleted_at IS NULL`；最好用 ORM 的全局作用域自动加
- **预防**：阶段4明确软删除标准，代码审查时查

## 坑11：索引太多导致写入慢

- **现象**：查询很快，但新增/编辑很慢
- **根因**：每个字段都建了索引，写入时要更新所有索引，开销大
- **解决方案**：只保留查询真正用到的索引，删除没用的索引
  - 用 `pg_stat_user_indexes` 看哪些索引从没被用过
- **预防**：阶段2建索引时只给 WHERE/JOIN/ORDER BY 字段建，不要盲目建

## 坑12：深分页 OFFSET 慢

- **现象**：前几页快，翻到第 100 页后越来越慢
- **根因**：`OFFSET 10000` 需要先扫描并跳过 10000 行，才能返回后面的 20 行
- **解决方案**：用游标分页（基于上一页最后一条的 id 或时间戳）
  ```sql
  SELECT * FROM orders WHERE id < $last_id ORDER BY id DESC LIMIT 20;
  ```
- **预防**：数据量大的表设计时就考虑游标分页

## 坑13：LIKE '%xxx%' 不走索引

- **现象**：搜索功能慢，数据量大了更明显
- **根因**：`LIKE '%关键词%'` 前后都有通配符，B-tree 索引用不上
- **解决方案**：
  - 前缀匹配 `LIKE 'xxx%'` 可以走索引
  - 全文检索：用 `to_tsvector` + `GIN` 索引
  - 模糊匹配：安装 `pg_trgm` 扩展，用 trigram 索引
- **预防**：阶段2设计搜索方案时选择合适的索引类型

## 坑14：并发更新丢失数据

- **现象**：两个人同时编辑同一条记录，后提交的覆盖先提交的，数据丢失
- **根因**：没有乐观锁或悲观锁，最后写入者覆盖
- **解决方案**：
  - 乐观锁：加 `version` 字段，更新时 `WHERE version = $1`，影响行数为 0 则提示冲突
  - 悲观锁：`SELECT ... FOR UPDATE` 锁住行（适合短事务）
- **预防**：阶段5并发测试时验证

## 坑15：改表结构锁表导致服务不可用

- **现象**：上线加字段或加索引时，网站卡了几分钟
- **根因**：某些 ALTER TABLE 操作会锁表，大表上执行时间长
- **解决方案**：
  - 加索引用 `CREATE INDEX CONCURRENTLY`（不锁表）
  - 加字段允许 NULL 或有默认值（快）
  - 大表结构变更在低峰期执行
  - 用数据库分支先验证，再合并到生产
- **预防**：阶段6发布时明确 Schema 变更原则

## 坑16：连接池耗尽

- **现象**：高峰期请求突然全部超时，日志报"too many connections"或获取连接超时
- **根因**：数据库连接数不够，或有连接泄漏（用完没释放）
- **解决方案**：
  - 检查连接池配置，增大最大连接数（但不要超过数据库 max_connections）
  - 检查是否有连接泄漏（长事务、未关闭的连接）
  - 用连接池（如 PgBouncer）复用连接
- **预防**：阶段5并发测试时监控连接数

## 坑17：AI 改完代码没测就发布

- **现象**：发布后发现新问题，或旧功能被破坏
- **根因**：过度信任 AI，未做验证
- **解决方案**：AI 每次改完，都在预览里测一遍再发布；发布后做冒烟测试
- **预防**：阶段4单模块自测、阶段5联调、阶段6线上冒烟

## 坑18：一次性让 AI 开发全部模块

- **现象**：一条指令让 AI 做完所有页面，结果多处问题交织、互相影响，返工成本高
- **根因**：没有模块切片和即开即测，错误在最后集中暴露
- **解决方案**：按模块切片，一次只做一块，预览自测通过再做下一块
- **预防**：核心原则"单模块闭环"，阶段4含分模块提示词模板

## 快速排查顺序

遇到问题按此顺序：

1. 看妙搭「接口日志」红色报错，确认是数据库错误还是应用错误
2. 数据库错误：看 SQL 语句和错误信息，直接在数据库执行该 SQL 复现
3. 慢查询：用 `EXPLAIN ANALYZE` 看执行计划，确认是否走索引
4. 检查是否有 N+1 查询（列表页逐条查关联）
5. 检查事务是否过长、锁等待（`pg_locks`）
6. 检查连接池是否耗尽（`pg_stat_activity`）
7. 对照本文件的坑位列表，看是否命中
