# 阶段5：测试验证

## 目标

模块自测之上做全量 + 跨模块联调，确保预览和发布环境都正常，数据正确，性能达标。

## 5.1 功能测试

### 预览环境

- [ ] 各模块列表数据正常显示
- [ ] 新增操作成功（返回 201，数据库有记录）
- [ ] 编辑操作成功（数据库字段已更新）
- [ ] 删除操作成功（软删除，deleted_at 有值，列表不再显示）
- [ ] 关联字段下拉正常，能正确保存
- [ ] 筛选分页正常
- [ ] 仪表盘数据正确（与数据库查询结果一致）
- [ ] 无控制台报错

### 数据库级核对（关键！不只看页面）

每次操作后，直接查数据库确认：

```sql
-- 新增后确认
SELECT * FROM orders ORDER BY id DESC LIMIT 5;

-- 编辑后确认
SELECT id, status, amount, updated_at FROM orders WHERE id = 123;

-- 删除后确认（软删除）
SELECT id, deleted_at FROM orders WHERE id = 123;

-- 统计页数据核对
SELECT COUNT(*), SUM(amount) FROM orders WHERE deleted_at IS NULL AND status = 'paid';
```

页面显示正确不代表数据库正确，必须查库确认。

## 5.4 性能测试

### 响应时间标准

| 接口类型 | 预期响应时间 | 超过则需优化 |
|---------|------------|------------|
| 列表查询（分页 20 条） | < 300ms | > 500ms |
| 详情查询 | < 200ms | > 300ms |
| 新增/编辑 | < 300ms | > 500ms |
| 统计聚合 | < 1s | > 2s |
| 搜索 | < 500ms | > 1s |

### 性能测试方法

1. **用浏览器 F12 Network 看接口响应时间**
2. **用 `EXPLAIN ANALYZE` 检查慢查询的执行计划**
   ```sql
   EXPLAIN ANALYZE
   SELECT * FROM orders WHERE status = 'pending' ORDER BY created_at DESC LIMIT 20;
   ```
   看是否有 `Seq Scan`（全表扫描），如果有，说明索引没生效。
3. **大数据量测试**：如果可能，导入 1000+ 条测试数据，看列表和统计是否还快
4. **并发测试**：多用户同时操作，看是否有锁等待或连接池耗尽

### 常见性能问题和优化

| 问题 | 原因 | 优化方案 |
|------|------|---------|
| 列表慢 | 全表扫描，没走索引 | 加索引，EXPLAIN 验证 |
| 列表慢 | N+1 查询 | 改 JOIN |
| 列表慢 | 拉全量不分页 | 加分页 |
| 统计慢 | 数据量大，聚合慢 | 加索引、预聚合表、物化视图 |
| 搜索慢 | LIKE '%xxx%' 不走索引 | 用全文检索或 trigram 索引 |
| 写入慢 | 索引太多 | 精简索引，只保留必要的 |
| 并发慢 | 长事务锁表 | 缩短事务，只把必要操作包在事务里 |

## 5.5 并发和事务测试

### 并发更新测试

模拟两个用户同时编辑同一条记录：
1. 用户 A 打开订单 123 的编辑页
2. 用户 B 也打开订单 123 的编辑页
3. 用户 A 提交修改（状态改为已发货）
4. 用户 B 提交修改（金额改为 100）

**预期**：不会丢失更新。要么 B 的修改基于 A 的最新值，要么提示"数据已被他人修改，请刷新"。

**实现方式**：乐观锁（加 `version` 字段，更新时 `WHERE version = $1`，影响行数为 0 则提示冲突）。

### 事务回滚测试

多表写入时，故意让第二步失败：
1. 新增订单（第一步成功）
2. 新增订单明细（故意传错数据，第二步失败）

**预期**：第一步也回滚，数据库里没有这条订单。

```sql
-- 验证
SELECT * FROM orders ORDER BY id DESC LIMIT 1; -- 不应该有刚才的订单
```
